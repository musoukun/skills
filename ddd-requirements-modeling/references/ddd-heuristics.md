# 実装方式の選び方と業務の動作の整理

要件に必要な仕組みを、単純な方法から選ぶ。
判断表は候補を絞るために使う。分類名や機能名だけで、複雑な実装方式を確定しない。

## 実装方式の判断

まず、金銭処理・分析・監査で何を記録し、何を再現する必要があるかを確認する。
次に業務ルールの複雑さを確認し、最後にデータ構造の複雑さを確認する。

| 要件で確認できること | 実装方式の候補 | 選ぶ理由 |
|---|---|---|
| 過去の出来事から状態や判断を再現する必要があり、現在の状態と通常の履歴保存では足りない | イベント履歴式ドメインモデル | 出来事の履歴を、状態を再現するための記録として扱う |
| 中核の業務に、入り組んだ状態の変化や複数の条件が関係する決まりがある | ドメインモデル | 中心となるデータと、守る決まりをまとまりとして扱う |
| 業務ルールは単純だが、関連するデータのまとまりと読み書きが複雑 | アクティブレコード | 保存対象のデータと、それを読み書きする処理をまとめる |
| 入力確認、計算、データの読み書きや変換を順に行えば足りる | トランザクションスクリプト | 業務の手順を普通の処理として書く |

金額や監査という言葉があるだけで、イベント履歴式にしない。現在の状態と変更履歴で必要な追跡ができるなら、その方法を候補にする。
ドメインモデルを選んでも、値オブジェクトや専用クラスを一式そろえる必要はない。採用条件は `../SKILL.md` に従う。
トランザクションスクリプトでも、データの読み書きはORMを使える。このスキルではORMを通す方針とする。アクティブレコードとORMの利用は同じ意味ではない。

### 複雑さの見分け方

| 観点 | 単純な場合 | 複雑な場合 |
|---|---|---|
| 入力と計算 | 必須項目の確認や決まった計算が中心 | 複数の業務条件が影響し合い、結果が変わる |
| 状態の変化 | 操作と結果の対応が明確 | 状態ごとに操作の可否が変わり、例外や制約が関係する |
| 情報の構造 | 少数の項目や独立した記録で足りる | 複数の関連や入れ子の情報を一緒に扱う |
| 言葉の説明 | 登録・表示・更新などで説明できる | 業務固有のルールや前提を説明しないと判断できない |

項目数が多いことだけを、業務ルールが複雑な理由にしない。

### 業務分類との突き合わせ

| 判断の組み合わせ | 確認すること |
|---|---|
| 中核としたが単純な処理で足りる | 差別化を生むのはどこか。業務ルールを読み落としていないか |
| 補完としたが複雑なモデルが必要 | 未確認の条件があるか。分類や業務の分け方が適切か |
| 一般としたが大幅な自前実装が必要 | 既製品が満たせない具体的な条件は何か |

食い違いは確定させず質問にする。分類に合わせるために部品を増やさない。
同じ文脈でも、業務によって適した方式が違う場合は、実装方式の行にその違いを書く。

## 処理と保存を分ける判断

| 状況 | 考える構成 |
|---|---|
| 単純な手順で処理できる | 受付、業務の処理、データの読み書きの役割が分かる形にする |
| 業務ルールを外部サービスやDBの都合から切り離す必要がある | 業務の判断を独立して扱い、外部との接続を別の処理にする。必要ならポートとアダプターを検討する |
| 一覧・集計と更新で、必要な情報の形が大きく違う | 更新用と参照用の処理やモデルを分ける。必要ならCQRSを検討する |
| 複数の業務を1つのアプリにまとめる | 業務ごとのまとまりを保ち、必要な情報を受け渡す |

層の数やディレクトリの形を先に固定しない。すべての境界に専用インタフェースを作ることを条件にしない。
保存や通知の具体的な判断は `ddd-tactical.md` に従う。

## 必要な動作の整理

出来事を手がかりに、誰の操作で何が変わり、どの業務へ伝わるかを整理する。これをイベントストーミングと呼ぶ。
要件文を材料に行い、実際に関係者と確認した結果と、こちらの仮置きを区別する。

| 種類 | 書き方 | 確認すること |
|---|---|---|
| 登場人物 | 業務での役割名 | 誰が操作や判断をするか |
| 外部システム | 要件に登場するシステム名 | 入力する側か、結果を受け取る側か |
| コマンド | 「〜する」 | 何を指示し、誰や何が実行するか |
| 業務イベント | 「〜された」 | 何が確定した出来事か |
| ポリシー | 「〜されたら〜する」 | 出来事を受けて自動的に何を行うか |

### 要件文から整理する手順

1. 対象とする業務と、達成したい結果を確認する。
2. 要件にある出来事を過去形で書き出す。
3. 通常の進み方を時系列に並べ、要件にある分岐や失敗時の動きを添える。
4. 順序、担当者、条件が不明な箇所を、未確認の点として残す。
5. 各出来事を起こす操作を「〜する」で書き、その操作を行う人や外部システムを対応付ける。
6. 出来事を受けて自動実行される操作があれば、ポリシーとして対応付ける。
7. 操作を判断するために必要な情報があれば、何を見るかを確認する。
8. 外部システムとの入力と通知を整理する。
9. 操作と出来事の対象を集約候補にまとめ、守る決まりから境界を確認する。
10. 同じ言葉の意味と担当範囲を確かめ、文脈の境界と突き合わせる。

各コマンドを誰や何が実行するか分からなければ、未確認と書く。要件にない操作、通知先、承認者を補って確定しない。
業務の切れ目は文脈を探す手がかりになるが、工程が変わるたびに別の文脈にしない。
単純な業務は要件に書かれた動作を表に整理すればよい。手順を満たすために動作を増やさない。

### 出力への反映

必要な動作は `../assets/output-template.md` の1つの表にまとめる。
集約、文脈、通知先が全体図と対応しているか確認する。動作の表には「何が変わるか」を短い1文で書く。
この段階では、各クラスや関数の入力・加工・出力を定める表は必須にしない。具体的な処理分割が必要になったときに詰める。

## 既存システムを整理する場合

現在の画面、コード、データ、業務の説明のうち、依頼に必要なものを確認してから現状を書く。
既存のフォルダ名やサービス名が、そのまま業務や文脈の境界とは限らない。

| 観察すること | 設計で確認すること |
|---|---|
| 同じ言葉が場所ごとに違う意味で使われる | 別の文脈に分ける必要があるか |
| 1つの業務変更で多数の場所を直す | 密接に関係する仕事を分断していないか |
| 相手のデータ形式を業務の各所で意識する | 受け渡しの部分で変換できるか |
| 業務ルールが複数の場所にある | 同じ決まりが重複していないか、管理する場所はどこか |
| 構造が複雑だが業務の理由が分からない | 業務担当者に具体的な操作や例外を確認できるか |

現状と提案を区別し、依頼に含まれない全面的な書き換えやサービス分割を提案の前提にしない。

## 設計結果の確認

- 業務の目的と、中心となる情報が対応しているか。
- 図、用語、動作、集約、テーブルの名前と関係がそろっているか。
- 集約の決まりを守る保存方法を説明できるか。
- 分類や実装方式を、要件に基づいて説明できるか。
- 必要な理由のない部品やパターンを足していないか。
- 未確認の判断に「（仮）」があり、答えによって設計が変わる質問に絞れているか。

実装時の確認方法を求められた場合は、単純な業務では受付から保存までの動き、複雑な業務では個々の決まりと同時更新、履歴を使う業務では状態の再現を検証対象にする。
