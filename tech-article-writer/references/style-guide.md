# 文体・表現ガイド（全タイプ共通）

過去記事8本から抽出した、この著者らしい書き方のルール。

## 全体構成の決まりごと

- **冒頭は「## TL;DR」**。2文構成にする（2026-08-23 にユーザーが直した完成形から）。
  - 1文目: 読者の今のやり方を「〜している人も多いと思います」とあるあるで描き、自分ごとにさせる
  - 2文目: 代わりの方法を言い、具体的なメリットを言い切り、「〜ので方法を紹介します」で締める
  - メリットは中身のない言い方で逃げない。
    ✗「参照画像として添付すると、メリットがたくさんあります」
    ○「参照画像として添付すると、生成の回数が減らせて、なおかつ一貫性が保ちやすいので方法を紹介します」
  - 手順の要約や補足・免責をTL;DRに詰め込まない（それらは本文でやる）。
    リポジトリやツールのURLがあるならTL;DR内か直後に貼る。
- **リンクは早く出す**。紹介対象のGitHub/公式サイトは記事の前半で必ず提示。
  URLは裸のまま行に置く。リンクをカードにして見せるブログが多いため。
- **締めは「## 感想」または「# 所感」**。1〜4文でゆるく締める。
  完璧を主張せず、「もっといい方法があるかもしれない」「自分もわかってないところがある」のような
  正直な一言や、「〜に活かしてください！」のような読者への呼びかけで終わるのがこの著者の型。

## 説明の順番（2026-08-23 の記事レビューで実際に指摘された反省）

- **完成形を先に見せる**。プロンプトや手順を説明するときは、「まずこんな感じの画像を出したい」
  ＋実物の画像を先に置いてから、それを出すためのプロンプト・手順を書く。
  理屈やコツの説明を先に長く続けない。読者は出来上がりを見て初めて説明を読む気になる。
- **指定・設定の説明は目的から書く**。「コマ割りされた1枚のシート画像を出したいので、
  フォーマットを次のように指定しておきます」のように「◯◯したいので」で始め、
  指定内容は箇条書きで並べる。指定の理屈（順番を逆にすると壊れる等）は本文でなく※の1行に落とす。
- **注意書き（:::message・※）は、何のための注意かを最初の1文で言う**。
  目的を1文で言えない注意書きは、読者にとってどうでもいい情報なので丸ごと削る。
  実際にあった失敗: 「キャプション帯の文言はプロンプトに書かない」という注意を目的なしで
  箇条書きにして、読者に「これは何のためにあるの？」と2回聞き返された。
- **読者の行動が変わらない豆知識は削る**。「1〜3語なら正確に出やすい」のような精度の細かい話は、
  読者のやることを変えないなら書かない。

## 文体・トーン

- 地の文は「です・ます」。ただし感想・本音パートは「〜と思う」「〜な気がする」「〜が最高」と
  口語に切り替わる。この切り替えが持ち味なので、全文を丁寧語で統一しない。
- 熱量はストレートに出す。「とにかく開発が早い」「凄すぎる！！」「最高だった」。
  ただし根拠（実測値・実例）とセットで使う。根拠なしの絶賛はしない。
- 自虐・正直な弱み開示を恐れない。
  実例:「僕はよくこのMCPがエラーで落ちるので、なぜかわかってなくてすみません」
  「Gitって自分もめっちゃわかってないなって思うことがある」
- 免責を書く。確立されていない手法なら「確実性が保証されていない」「期待し過ぎずに」と冒頭か末尾で断る。

## 強調・視覚要素

- **太字**は「一番伝えたい一文」に使う。1セクション1〜2箇所まで。段落全体を太字にしない。
- 対応関係・比較・選択肢は**表**にする（用語対応表、Before/After、フラグの組み合わせ、コスト比較）。
- 注意・判断・補足は次の記法を使う:
  - `:::message` … 注意書き、テスト結果の判断（○×）など
  - `:::details タイトル` … 元画像・長い出力・折りたたみたい補足
- スクショ・画像は多め。手元に画像がない場合は
  `![](ここに〇〇のスクショ)` の形でプレースホルダを置き、何を撮るべきかを書く。
- 補足の一言は「※」で行頭に付ける（例: 「※Ollamaでローカルモデルを使う場合は…」）。

## わかりやすさの粒度

- 専門用語には日常語の補足を付ける。形式は「用語（＝日常語の一言説明）」または「日常語（物理名）」。
  実例: 「Ollama（ローカルで動く大規模言語モデル）」「競合（コンフリクト）」「一時保管（stash）」
- **定義していない用語をいきなり出さない**。記事の中で初めて使う言葉は、
  先に「それが何か」を説明してから使う。説明できない・説明が面倒な言葉なら、
  その言葉自体を使わずに普通の文で書く。
- **平易な言葉で書く。圧縮しない**。長い説明が必要な場面でも、次の圧縮をしない:
  - オリジナルの比喩表現やラベルを作らない（作った本人にしか通じない暗号になる）。
    実際にあった失敗: プロンプトの書き方の説明で、何の説明もなく
    「シートの『入れ物』と『中身』を分けて書く」と書き、読者に「入れ物って何？」となった。
    ✗ 入れ物（グリッド・番号タグ・キャプション帯）を先に確定させる
    ○ シート全体の見た目（コマを何列×何行で並べるか、番号を付けるか）を先に書き切ってから、
      コマの中身を番号順に並べる
  - 文字数を減らすために、意味の複雑な熟語や専門用語をつなげない
    （✗「共通実行口への集約」 ○「33箇所に散らばっていた処理を、1つの入り口を通る形に整理した」）
  - 名詞を「の」「への」でつないだ見出し風の文にしない。主語と述語のある普通の文で書く
  - 長くなってよいので、文を切って1文1情報で書く
- 説明の順序は **概念 → 具体例 → コード**。いきなりコードから始めない。
- コードは最小限の断片だけ。長い実物は載せない。「やっていることは〜だけです」と
  コードの前後に日本語の要約を必ず添える。
- 手順は番号付きリストで1手順1アクションに刻む。書き方は読者への声かけ調で平易に
  （例:「絵コンテシートを画像生成しましょう」）。仕様書のような体言止めの羅列にしない。
- **手順リストの各行は骨だけにする**（2026-08-23 にユーザーが直した完成形から）。
  成果物の形式やカッコ書きの補足を手順の行に混ぜない。詳細は後のセクションで説明する。
  ✗「カットごとに文章化します。各カットに「見出し・説明1〜2文・カメラ指定」を書きます（LLMに書いてもらってOK）」
  ○「大まかなストーリーを決めて、カットごとに文章化します。」
- **手順は前の手順とのつながりを明示する**。「1.の内容を画像化します」のように、
  前の手順の成果物を受けて何をするのかを書くと、流れが1本の線で追える。
- 例示のプロンプトやコードには見出しに「（サンプル）」と明記する。
- カメラ用語のような一般知識の表を載せるときは、「調べたら出てくるとは思いますが、
  一般的な指定方法を記載しておくので参考にしてください」のような前置きを付けてから表を出す。
  自分の発見のように見せない。
- 数値は具体的に出す（「114棟 → 543棟」「0% → 100%」「$0.0019 → $0.0026」）。
  効果を語るときは Before/After の実測値で示す。
- 「やりたいこと」を独立セクションにして**太字1文で言い切る**のが特徴的な型。
  実例: 「**AIに話しかけるだけでGitが裏側で動く仕組みをSkillsで実現したい。**」

## 正直さのルール（この著者の信頼の源泉）

- うまくいかなかった例・失敗例も載せる（例: G-Eval採点が横ばいで改善が空回りした話）。
- 制限・不具合・ライセンスの注意点は隠さず1セクション割く（例: Mastraのライセンス、Presentonの画像生成不具合）。
- あいまいなことは「〜っぽい」「〜だと思う」「要確認」と正直に書く。断定できないことを断定しない。
- 感想パートで実体験風のエピソードや効果（「やり直し回数が減った」等）を作らない。
  ユーザーが実際に言った体験・主張だけを書く。
- issue番号や公式ドキュメントなど根拠のURLを添える。

## タイトルの付け方

過去記事の実例:
- 「Mastraで爆速AIエージェント開発したい人向けサンプル」
- 「多くの人にとってGitが難しいという課題をスキルでなんとかしたい」
- 「スクショに注釈を描き込む作業をSkillsに任せると最高だった」
- 「無料のAIスライド（PPTX）生成ツールPresentonのクオリティが高め」

傾向: 口語のまま、体験や気持ちを入れる（〜したい / 〜が最高だった / 〜が高め）。
釣りタイトルにはしないが、堅い論文調（「〜の検討」「〜に関する考察」）にもしない。

## セルフチェックリスト

書き終えたら確認する:
- [ ] TL;DRだけ読んで要点とリンクにたどり着けるか
- [ ] 完成形（出したい画像・結果）をプロンプトや手順より先に見せているか
- [ ] 注意書きはすべて「何のための注意か」が最初の1文でわかるか
- [ ] 実測値・数値は素材にあるものだけか（想像で数字を作っていないか）
- [ ] 素材にある「うまくいかない点・注意点」を漏らさず載せたか（素材に無いものを創作していないか）
- [ ] 専門用語に日常語の補足が付いているか
- [ ] 自作の比喩・造語や、熟語をつなげた圧縮表現を使っていないか（平易な普通の文になっているか）
- [ ] 定義せずにいきなり出している用語がないか（初出の言葉は先に説明しているか）
- [ ] コードより日本語の説明が主になっているか
- [ ] 締めが「感想/所感」でゆるく終わっているか
- [ ] 全文が丁寧語で固まっていないか（感想パートに口語があるか）
