# Before/After キャプチャの鉄則（issue-loop Step 4-5 / 4-6c）

撮る前に必ず読む。Before は「自分の環境で再現した現状」を撮るのが正しい。お客さんが貼った画像は「報告」であって、Before の代わりにはしない。

## 1. 撮る前に「そのポートを配信しているのが自分のフォルダか」を確かめる

worktree を複数使っていると、別の worktree の開発サーバーが同じポートを使っていて、**自分のコードと違う画面を撮ってしまう**ことがある。

```bash
LPID=$(lsof -nP -iTCP:<ポート> -sTCP:LISTEN -t | head -1)
lsof -p "$LPID" | awk '$4=="cwd"{print $NF}'   # 配信元のフォルダが出る
```

- 配信元が**自分の worktree** → そのまま使う
- 配信元が**別の worktree** → **止めない**（相手の作業を壊す）。自分のサーバーを**別のポート**で起動して、そちらで撮る

## 2. 表や要素は、決め打ちの座標で切り抜かない

固定の x/y/幅/高さで切り抜くと、表の幅と合わずに見切れる。Playwright で対象要素（見出し〜表）の `boundingBox()` を取って、その範囲を撮る。横に長い表は、ビューポートを十分広くしてから撮る。

## 3. Before と After を切り替えるのに `git stash` を使わない

差分が無い状態で `git stash push` → `git stash pop` をすると、**無関係な古い stash を pop して作業ツリーを壊す**ことがある。版の切り替えは checkout で行う。

```bash
git checkout origin/main -- <file>   # 変更前の版にする（Before を撮る）
git checkout HEAD -- <file>          # 自分の版に戻す（After を撮る）
```

ホットリロードの反映前に撮ると前の版が写る。狙った版にしか無い文字が画面に出るまで待ってから撮る。

## 4. データ系の Before

画面ではなく出力が変わる issue は、現状の出力を実データで取る（API のレスポンス、AI の応答 1〜2 件など）。

## 5. テストを流す前に、データを消さないか確かめる

e2e テストの準備処理が、毎回データベースを初期化するリポジトリがある。手作りのデータを Before に使うつもりでテストを流すと、そのデータごと消える。

- テスト内でデータを作ってから撮る形にすると、消えても毎回作り直せる
- 消したくないデータを撮るだけなら、テストの仕組みを通さない単発の Playwright スクリプトで開いて撮る

## 6. ページを開いたときに初めて作られるデータがある

一括処理では作られず、**その画面を初めて開いたときに生成が始まる**データがある。データベースを見て待ち続けても来ない。「出ない」ときは、まず「そのページを開いたことがあるか」を疑う。

## 7. それでも実画面が出せないときは止まって質問する

自分でデータをでっち上げない。「どのデータで再現すればいいか」をユーザーに聞く。

## 8. After

Before と同じ手段で撮る。実装が組み込まれた本物の画面を撮る。確認用の一時ページやプレビュー route を作ってそれを撮らない。
