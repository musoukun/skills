# 自作モノ公開型（arnis-jp / egit / screenshot-annotate の型）

自分で作ったツール・スキル・OSS改造を公開する記事の構成。

## この型の狙い

「何に困っていて、何を作ったら、どうなったか」の物語で読ませる。
技術詳細より先に、課題とやりたいことを日常語で腹落ちさせるのがポイント。

## 構成テンプレート

```
## TL;DR
（何を作ったか1〜2文＋リポジトリURL。前作があるなら前回記事へのリンク）

## 〔課題〕
（誰が・何に困っているかを具体的に。見出しは「Gitは便利だけど、使える人が限られている」
 のような口語の文でよい）

## やりたいこと
（**太字1文で言い切る**。この記事の背骨になる文）

## 導入方法 / 利用方法
（リポジトリURL、インストール手順、実行方法。読者が試すのに必要な情報を先に出す）

## 設計で考えたこと / 仕組み
（工夫を1つずつ小見出しで。「〜を全部置き換える」「〜を打たせない」のような
 方針の見出し＋理由＋実例。データの流れは矢印の縦フローで図解してよい）

## 実際の使い方の例 / 実測
（会話例・作例・Before/Afterの数値。自作ツールの記事は「動いている証拠」が命）

## 感想
（1〜3文。正直な一言で締める）
```

## この型で特に効く書き方

- **課題は「人」で語る**。「バックオフィスの人が、ファイルの変更履歴を残したいだけなのに
  Gitの概念を学ぶ必要があるのはしんどい」のように、困っている人の場面を書く。
- **やりたいことは1文**。仕様の羅列にせず「AIに話しかけるだけでGitが裏側で動く仕組みを実現したい」
  まで削る。
- **対応表が武器**。「Git用語 → 置き換えた言葉」「種類コード → Arnis側での扱い」のように、
  設計判断は表で見せると一気に伝わる。
- **動作例は実物を貼る**。会話型ツールなら実際のやりとりをコードブロックで、
  画像系なら作例を `:::details 元画像` との対比で載せる。
- **実測値で効果を示す**。「OSM単体 114棟 → 合計 543棟」のように Before/After を表で。
- 実装コードは「読ませるための最小断片」だけ。関数まるごとは貼らず、
  肝の数行＋日本語の説明にする。
- 安全面・制限（自動実行しない操作、対象外のケース）も1セクション割いて正直に書く。
