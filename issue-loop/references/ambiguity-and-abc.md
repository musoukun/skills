# 2種類の曖昧さ（設計 HTML と ABC 質問の使い分け）

issue-loop の Step 4-3（設計 HTML）〜 4-3.5（ABC 質問）に入る前に読む。

曖昧さには **2 種類** あり、潰す道具が違う。片方だけだと事故る。

- **プロダクト方向の曖昧さ**（どんな見た目・体験にするか）→ **設計 HTML** で、決める人が絵を見て直感で決める。これがあるから「この案でいこう」が成立する
- **実装方向の曖昧さ**（スコープ / 作りの方針 / 検証 / 出し方 / データの扱い / 権限・ユーザーに見える挙動）→ **ABC 質問**で 1 問ずつ潰す。見た目が決まっても、ここは別に残る。聞かないと、エージェントが黙って決めてしまう所

順番は、**設計で方向を承認 → 残る実装方向を ABC で確認 → plan に両方を書く → 実装**。

## 選択肢の見せ方は2レーン

各曖昧さを「**見た目が変わるか**」で振り分け、見せ方を変える。UI の話を文字の3択で聞くと伝わらない。

- **見た目が変わる曖昧さ**（レイアウト・列の向き・ボタンの位置・表示の密度 等）
  → 選択肢 A/B/C を **1 枚の HTML に横並びで描き**、ブラウザで開いて見せ、**番号で選んでもらう**
- **見た目に出ない曖昧さ**（データの持ち方・状態の保存・分割の仕方・権限・並び順 等）
  → **テキストの A/B/C** で AskUserQuestion で聞く

1 つの issue で両レーンが混ざってよい。どちらのレーンも、選択肢には「**結果＋その案だと実装が何になるか**」を添え、`おすすめ:` を 1 行付ける。

## ABC 質問のルール

形だけの確認になると、決める人の時間を奪うだけで逆効果。以下を必ず守る。

1. **聞いていいのは 6 カテゴリだけ**：スコープ / 作りの方針 / 検証 / 出し方 / データの扱い / 権限・ユーザーに見える挙動。**このどれかが選択肢で変わる時だけ聞く**
2. **1 問ずつ。最大 3 択**。現実に選ばれうる案だけ並べ、明らかに選ばれない「当て馬」を入れない。各選択肢に「結果＋実装」を添え、最後に `おすすめ:` を 1 行。前の問いに答えが出てから次の問いへ
3. **コード・テスト・リポジトリの決まりを読めば分かることは聞かない**
4. **割れていなければ聞かない**。A（明確）の issue は質問ゼロでよい。その場合は「実装方向に分岐なし」と 1 行書いて plan へ進む

## やってはいけないこと

- 実装方向が割れているのに確認せず、黙って決めて実装する
- 当て馬を並べる／コードを読めば分かることを聞く／割れてもいないのに質問を作る
- 見た目が変わる曖昧さを文字の 3 択で聞く
