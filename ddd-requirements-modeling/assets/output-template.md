# 〔システム名〕の設計の土台

〔誰が、何のために、何をするシステムかを 1 文で言い切る〕

## 1. 全体像

### 1.1 どんな主体ができて、どうつながるか

```mermaid
flowchart TB
    subgraph D1["〔業務領域名〕（補完・レベル1）"]
        A1["〔主体A〕"]
    end
    subgraph CTX1["〔文脈名〕（中核・レベル3）"]
        B1["〔集約B〕"]
        B2["〔集約C〕"]
    end
    subgraph EXT["外部・既存"]
        E1["〔既存システム〕"]
    end
    E1 -->|"〔連係パターン〕"| B1
    A1 -->|"〔何を渡すか〕"| B1
    B1 -->|"〔何を渡すか〕"| B2
    B1 -.->|"〔〜された〕を知らせる"| A1
```

矢印は上流から下流へ、材料が流れる向きに引く。実線は材料を渡す（下流が上流を ID で参照する）、点線は出来事を知らせる。

図の読み方を 2〜3 行で書く。どこが中心で、何が起きると何に伝わるか。中の箱は主体、つまり業務の中心となるデータ、と初出でここに書く。レベル3の業務領域があるときだけ、その外枠は区切られた文脈（Bounded Context）、中の箱は集約（Aggregate）のルート、と書く。

### 1.2 中核の業務領域とそれ以外

| 業務領域 | 種類 | 一言の理由 | 方針 |
|---|---|---|---|
| 〔領域〕 | 中核 | 〔競合との差になる点〕 | 自前で作り込む |
| 〔領域〕 | 一般 | 〔既製品で済む理由〕 | 既製品・外部サービス |
| 〔領域〕 | 補完 | 〔無いと困るが差にならない理由〕 | 素直に作る |

### 1.3 作り方の判定

既定はレベル1。要件文に兆候があるときだけ上げる。

| 業務領域 | レベル2の兆候 | レベル3の兆候 | 段階 | 構成 |
|---|---|---|---|---|
| 〔領域〕 | なし | なし | レベル1 | MVC |
| 〔領域〕 | 「〔要件文の引用〕」 | なし | レベル2 | ポートとアダプター |
| 〔領域〕 | 「〔引用〕」 | 「〔要件文の引用〕」 | レベル3（仮） | ドメインモデル＋ポートとアダプター |

- 技術構成: Next.js（App Router）、Prisma、SQLite、Tailwind CSS 4 以上。
- 別サーバー: なし。〔立てるなら Hono か FastAPI と、当たった条件を 1 行〕
- テストから先に書く業務領域: なし。〔要件が不明瞭な業務領域があれば、その名前と関係する「決めてもらうこと」の番号〕
