# 手法・ノウハウ型（AI自己生成テスト / Deepwiki駆動開発 の型）

開発のやり方・ワークフロー・考え方を共有する記事の構成。

## この型の狙い

「自分はこうやっている。割と効く」という実践知の共有。
体系化された方法論ではなく個人の試行錯誤メモである、と正直に断った上で、
読者が今日から真似できる粒度まで手順を具体化する。

## 構成テンプレート

```
## TL;DR / 前置き
（どんな課題意識から生まれた方法か。免責（「※確実性が保証されていない」など）は、
 素材やユーザーの言葉にあるときだけ書く。型に合わせて足さない）

## 〔従来のやり方との違い / なぜ既存の方法では足りないか〕
（ユーザーの素材にこの比較・理由があるときだけ書く。素材に無い「なぜ崩れるか」の
 理屈をそれらしく創作してはいけない。無ければこのセクションごと省く）

## 方法
（手順を番号付きで。実際に使う指示文・プロンプトはそのまま載せる）

## 実例
（生成物・スクショ・やりとりの実物。「うまくいかない例」や失敗パターンは
 ユーザーの素材にあるときだけ載せる。トラブルシューティング表を勝手に作らない）

## メリット
（1メリット1小見出し。「テストケース作るのが楽」のような素直な言葉で）

## 〔応用・自動化の展望〕
（「〜するともっといいかも」の粒度でよい。やっていないことはやっていないと書く）

## 感想
（「もっといい方法があるかもしれない」系の開かれた締め）
```

## 自分の作った物を例にして、やり方を伝えるとき

例:「Skills を育てる方法を、Minecraft の建物を作るスキルを例に伝える」。
主役はやり方なので、例に使う物の紹介は短くし、結論（コツ）を前半で先に言う。

```
## TL;DR
# 〔例に使う物の完成形：成果を口語で言い切る〕（画像）
# 〔例に使う物の前提〕（土台・前の記事のリンク）
## 〔やり方のコツ（結論）〕（箇条書きで2〜3個。ここで先に言い切る）
# 実例に沿って解説
## やりたいこと
## 〔例の仕組み・流れ〕
### 〔失敗・課題ごとに1つ。時間の順〕（工夫の直後に著者の考えを :::message で）
（1つの苦労が長いときは、「失敗した」「直してみた」「原因を考えた」「工夫した」をそれぞれ小見出しに分ける）
## 〔繰り返して確かめた結果〕
# 付録：〔関連する他の取り組み〕
## 今後やりたいこと
## 感想
## 参考
```

## この型で特に効く書き方

- **免責が信頼を作る**。手法系は言い切るほど嘘くさくなる。
  「絶対大丈夫とも限らない」と書くのがこの著者の型。
- **指示文・プロンプトは実物を貼る**。読者がコピペして試せることが手法記事の価値。
- **失敗例と判断例は素材にあるものだけ**。素材にあるなら「この出力はここがNG（✖）、
  ここは確認できた（○）」を :::message で示すと読者が自分で判断できる。
  素材に無い失敗例・直し方を想像で作るのは捏造。
- **サイクルを1行で図示**してよい。
  例: 「テストケース生成 → 自問自答 → 結果確認 → プロンプト調整 → 再テスト」
  （回答文では矢印チェーンを避けるが、記事内でワークフローを示す図としては使ってよい）
- **やっていないことは展望として分離**。「自動化するともっといいかも」のように、
  実践済みと構想を混ぜない。
