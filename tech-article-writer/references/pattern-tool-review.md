# ツール・OSS紹介型（Mastra / Presenton / Opik の型）

既存のツール・フレームワーク・サービスを試して紹介する記事の構成。

## この型の狙い

「このツール、名前は聞くけど実際どうなの？」という読者に、
セットアップから実際に動かした画面まで見せて、導入判断ができる状態にする。
売り込みではなく「使ってみた人の正直なレポート」の距離感で書く。

## 構成テンプレート

```
## TL;DR
（何のツールか＋一番の売りを2〜3文。「〜が優れているので紹介したい」）

## 〔現状の課題 / 既存ツールとの違い〕
（このツールが要る背景。類似ツールに触れて「多くは〜まで。これは〜までできる」と位置づける）

## 〔ツール名〕とは
（GitHubリンク・ライセンス・スター数・対応OS・対応プロバイダーなど事実を箇条書きか表で）

## セットアップ
（インストール手順。Docker/デスクトップ等の選択肢があれば小見出しで分ける。
 設定ファイルは実物を短く貼る）

## 実際に使ってみる
（一連の操作をスクショ付きで。入力に使った実データ・プロンプトはそのまま載せる）

## 〔特に良かった機能〕
（1機能1セクション。「ここが優れている点：」のような箇条書きで理由を添える）

## 注意点 / 制限
（ライセンス制約・既知の不具合・破壊的変更など。issue番号やURLを根拠に添えて正直に）

## まとめ
（導入判断の一言＋注意の再確認。ゆるく締める）
```

## この型で特に効く書き方

- **一番の売りを断言する**。「一番の売りだと思っている点は『npmのプレイグラウンドですぐにテストできる』ところです」
  のように、機能一覧の中から自分の推しを1つ選んで太字で言い切る。
- **実際に入力したものを全部見せる**。試したプロンプト・Markdown・設定ファイルは省略せずそのまま載せる。
  読者がコピペで再現できることが価値。
- **機能の羅列は表かリストで圧縮**し、本文は自分が実際に使った機能に絞って書く。
- 「大丈夫なこと / ダメなこと」の対比リストはライセンスや制限の説明で有効
  （Mastra記事のELv2の説明が見本）。
- 不具合は「〜の不具合が報告されています（#462、#402）」と issue 番号付きで書き、回避策まで添える。
