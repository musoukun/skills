# GoF パターンの選び方（判断表）

出典は TECHSCORE のデザインパターン解説（https://www.techscore.com/tech/DesignPattern/）。
各パターンの「目的」「使うとき」は、上記サイトの各ページに書かれている内容だけを根拠にしている。

## 23 を 11 に絞った理由

GoF は 23 パターンだが、この表には 11 だけ載せる。2026 年時点の TypeScript のような言語では、残りの 12 は言語機能や標準ライブラリで済むか、別のパターンに寄せられるか、実務でほぼ出番が無い。
根拠は `references/gof-review-2026.md`（2026-09 の調査。Peter Norvig の「動的言語では 23 のうち 16 が不要か単純になる」という分析と、2021〜2026 年の再評価記事）。

内訳は次のとおり。

| 区分 | 数 | パターン |
| --- | --- | --- |
| 残す | 10 | Adapter、Decorator、Proxy、Composite、Builder、Observer、Mediator、State、Command、ChainOfResponsibility |
| 特別枠 | 1 | Facade（判断基準を満たすときだけ） |
| 別のパターンや素朴な書き方に寄せる | 4 | TemplateMethod、Bridge、AbstractFactory、Memento |
| 言語機能で足りる | 6 | Singleton、Iterator、Strategy、FactoryMethod、Prototype、Visitor |
| ほぼ使わない | 2 | Flyweight、Interpreter |

表に無い 12 が当たりそうなときは、パターン名を提案せず「言語機能で済む」「〜に寄せる」と 1 行で書く。書き方は末尾の「表に入れないもの」を見る。

techscore の基本ページにある前提も守る。実際の開発で 23 に「ぴったりと当てはまることなんて、そうそうない」。無理に当てはめない。

## 残す 10 パターン

### Adapter
- 目的: インタフェース（＝呼び出し方の決まり）に互換性の無いクラス同士を組み合わせる。
- 役割: 既存の機能を持つクラス、要求される側のインタフェース、その両方をつなぐ Adapter。
- 使うとき:
  - 優れたメソッドがあるが、これまで使っていたメソッドと呼び出し方が違い、乗り換えると変更が大きい。
  - 既存の機能をそのまま使いつつ、要求された呼び出し方に合わせたい。
- 2026 年の実態: 外部 API の応答や ORM の型を、アプリ内部の型に変換する薄い関数として生き続けている。言語が何でも境界は発生する。
- 出典: https://www.techscore.com/tech/DesignPattern/Adapter/Adapter1.html と https://www.techscore.com/tech/DesignPattern/Adapter/Adapter2.html

### Decorator
- 目的: 飾り枠と中身を同一視して、柔軟な機能拡張の方法を提供する。
- 役割: 共通インタフェース、基本となる具体クラス、同じインタフェースを実装しつつ拡張対象のインスタンスを保持する Decorator。
- 使うとき:
  - 機能を 1 つずつかぶせるように追加したい。
  - 継承だと組み合わせの数だけクラスが増えてしまう。
- 2026 年の実態: 高階関数でログ・リトライ・キャッシュを重ねる形。TypeScript にはデコレータ構文もある。
- 出典: https://www.techscore.com/tech/DesignPattern/Decorator.html

### Proxy
- 目的: 代理人オブジェクトが要求を受け取り、代理人でできる処理は代理人が、できない処理は本人が引き受ける。
- 役割: 実際の処理を行う本人オブジェクト、要求を受け取る代理人オブジェクト、要求を出すクライアント。
- 使うとき:
  - 本人がすべての要求に応じなくてもよいようにしたい。
  - クライアントが本人と代理人を区別しなくてよいようにしたい。
- 2026 年の実態: API クライアントのラッパー、遅延読み込み、アクセス制御。JavaScript 自体に Proxy オブジェクトがある。
- 出典: https://www.techscore.com/tech/DesignPattern/Proxy.html

### Composite
- 目的: 容器と中身を同一視して、再帰的な構造を扱いやすくする。
- 役割: 共通インタフェース、単独の要素である Leaf、複数の要素を保持する Composite。
- 使うとき:
  - ファイルとフォルダのように、入れ物と中身を区別せず同じ操作で扱いたい。
  - 新しい要素の種類が増えても、入れ物側のクラスを直したくない。
- 2026 年の実態: UI コンポーネントの木、コメントの入れ子、組織図。木構造を持つ業務がある限りなくならない。
- 出典: https://www.techscore.com/tech/DesignPattern/Composite.html

### Builder
- 目的: 同じ作成過程で、異なる表現形式の結果を得る。
- 役割: Director（＝作成過程を決める役）と Builder（＝表現形式を決める役）に分かれる。Director は具体的な Builder の実装を知らない。
- 使うとき:
  - 複雑なオブジェクトの生成手順が繰り返し使われる。
  - 手順は同じで、出来上がりの形式だけを変えたい。
- 2026 年の実態: 必須項目がそろうまで完成できないことを型で強制したいときに使う。独立した項目が 2〜3 個ならオブジェクトリテラルで足りる。
- 出典: https://www.techscore.com/tech/DesignPattern/Builder.html

### Observer
- 目的: 観察対象が状態変化した際に、そのインスタンス自身が観察者に通知する。
- 役割: 観察者の登録と通知を行う Subject、通知を受け取る update メソッドを持つ Observer、それぞれの具体クラス。
- 使うとき:
  - ある対象の状態変化を、複数の関係者が把握する必要がある。
  - 観察者を後から追加したり、観察対象を増やしたりしたい。
- 2026 年の実態: EventEmitter、DOM のイベント、業務イベントの配信。単純ならこれで足り、複数の流れを合成するときだけ RxJS のような道具に進む。
- 出典: https://www.techscore.com/tech/DesignPattern/Observer.html

### Mediator
- 目的: 仲裁人の役割を持つクラスが全体の状況を把握し、各オブジェクトに指示を出す。
- 役割: 調整役の Mediator インタフェースと具体的な Mediator、相談や指示を受ける Colleague インタフェースと具体的な Colleague。
- 使うとき:
  - オブジェクト同士が互いに調整し合っていて、関係が複雑に絡んでいる。
  - 複雑に絡み合った条件を満たさないと有効にならないボタンのような入力画面を作る。
  - 条件が変わったときの直しやすさを上げたい。
- 2026 年の実態: 状態管理ライブラリが中央の調整役になる形。やりとりが双方向・多方向になったときに Observer から進む。
- 出典: https://www.techscore.com/tech/DesignPattern/Mediator.html

### State
- 目的: 「状態」をクラスとして表現し、状態によって振る舞いが変わることに対応する。
- 役割: 状態を保持して委譲する Context、状態のインタフェースである State、各状態の振る舞いを実装する ConcreteState。
- 使うとき:
  - 複数の状態があり、状態ごとに振る舞いが大きく異なる。
  - 状態を追加するたびに、すべての if 文の分岐を見直している。
- 2026 年の実態: 判別可能な共用体と switch で状態ごとの型と処理を分ける。網羅性チェックで「あり得ない状態」をコンパイル時に防げる。遷移が複雑なら状態機械のライブラリ。
- 出典: https://www.techscore.com/tech/DesignPattern/State.html

### Command
- 目的: 要求自体をオブジェクトにして、そのオブジェクトを引数に渡せるようにする。
- 役割: 実行メソッドを持つ抽象の Command、実際の要求内容を実装する具体的な Command、実際の処理を行う Receiver、Command を作って実行する Client。
- 使うとき:
  - 送りたい要求の種類が増え、引数の数や種類を増やす方法が限界にきている。
  - 要求の種類を増やすたびに、呼び出す側と呼び出される側の両方を直している。
  - 既存の要求を組み合わせて新しい要求を作りたい。
- 2026 年の実態: ジョブキューに積むジョブ、Redux の action、undo/redo。「操作をあとで実行できるデータとして持ち運ぶ」発想は非同期処理が増えた今ほど価値がある。実装はクラスでなく素朴なオブジェクトと関数で足りる。
- 出典: https://www.techscore.com/tech/DesignPattern/Command.html

### ChainOfResponsibility
- 目的: 複数の責任者を鎖状につなぎ、自分で判断できるものは自分で判断し、できないものは次の責任者に任せる。
- 役割: 判断メソッドと次の責任者を持つ抽象的な責任者、自分の判断範囲を定義する具体的な責任者。
- 使うとき:
  - 金額や内容によって、誰が決裁するかが段階的に変わる。
  - 判断の流れである鎖を、後から組み替えたい。
- 使わない方がよいケース: 毎回鎖をたどるため、処理速度が遅くなることが考えられる。速度を重視するか柔軟性を重視するかで判断する。
- 2026 年の実態: 名前は「ミドルウェア」に変わったが、認証・ログ・検証を順番に通す仕組みとして毎日使われている。
- 出典: https://www.techscore.com/tech/DesignPattern/ChainOfResponsibility.html

## 特別枠: Facade

- 目的: 複雑に関係し合う多数のクラスに対して、窓口となるクラスを用意し、利用者が単純に使えるようにする。
- 役割: 窓口となる Facade、統合される既存のクラス群、Facade を通して使うクライアント。
- 使うとき:
  - 正しい順番でメソッドを呼ぶ必要があり、手順が複雑になっている。
  - 利用者に複数クラスの使い方を覚えさせたくない。
- 出典: https://www.techscore.com/tech/DesignPattern/Facade.html

特別枠にした理由は、TypeScript ではモジュールの export が Facade の役目をそのまま果たすので、ほとんどの場合はパターン名を付けるまでもないから。ただし次の判断基準を満たすときは、設計書に Facade として書く価値がある。

### Facade を書く判断基準

次の 3 つのうち 2 つ以上を満たすときだけ Facade を提案する。

1. 窓口の裏に、外部システムや既存システムが 2 つ以上ある。1 つなら Adapter。
2. 裏の呼び出しに順番や前提条件がある。「A を呼んでから B」「B は A の結果が要る」のように、順番を間違えると壊れる。順番が無いなら、ただの関数のまとめでよい。
3. 利用者が複数いて、裏の都合を知らせたくない。画面が 1 つで利用者も 1 つなら、そのままモジュールで済む。

満たさないときは、パターン名を付けず「1 つのモジュールにまとめる」と書く。

## 表に入れないもの（12 パターン）

当たりそうなときは、パターン名を提案せず次の 1 行で書く。

| パターン | 書き方 | 理由 |
| --- | --- | --- |
| TemplateMethod | 骨組みの関数にコールバックを渡す。パターン名は付けない | 継承でなく関数を渡す形にすると Strategy と同じになり、Strategy は関数そのもので足りる |
| Bridge | 実装をコンストラクタや引数で渡す。パターン名は付けない | 関数やオブジェクトを渡すだけで差し替えられる |
| AbstractFactory | 一式を返すファクトリ関数を 1 つ書く。パターン名は付けない | 型が値として渡せるので、専用のクラス階層が要らない |
| Memento | 過去の状態を配列で持つ、または Command の逆操作にする | 書き換えないデータ構造なら、状態の履歴を持つだけで戻せる |
| Singleton | ES モジュールで 1 回だけ作って export する | モジュールは 1 度しか評価されない。getInstance 方式はテストしにくく批判が多い |
| Iterator | for...of とジェネレータを使う | 言語に組み込まれている |
| Strategy | 関数を渡す。ただし下の「関数で差し替えるときの書き方」に従い、名前付き関数にして switch か対応表で選ぶ。無名関数を 1 行に詰めない | 関数が第一級なので、インタフェースと実装クラス群が要らない |
| FactoryMethod | 生成する関数を 1 つ書く | 同上 |
| Prototype | spread や structuredClone で複製する | JavaScript 自体がプロトタイプ委譲 |
| Visitor | 判別可能な共用体と switch で書く | 網羅性チェックが、型を足したときの対応漏れをエラーにしてくれる |
| Flyweight | 使わない | メモリ最適化が要るのはゲームや大量描画のような特殊な領域だけ |
| Interpreter | 既存のパーサライブラリを使う。木の扱いは Composite | 独自のミニ言語を自作する場面が稀 |

## 関数で差し替えるときの書き方

Strategy、TemplateMethod、Bridge、FactoryMethod を「関数を渡す」に寄せたとき、読みやすさは別に守る。根拠と例は `references/ts-function-dispatch-readability.md`。

| ケースの数 | 書き方 |
| --- | --- |
| 3〜4 個までで、増える見込みが薄い | 名前付き関数を先に定義し、switch で呼び分ける。default に never を受けるヘルパーを置いて、ケース漏れをコンパイルエラーにする |
| 5 個以上、または一覧で見渡したい、増減が多い | 名前付き関数を先に定義し、`satisfies Record<共用体, 関数の型>` の対応表に 1 行 1 ケースで並べる |
| 値の形（入れ子のオブジェクトなど）で分岐する | ts-pattern のようなライブラリを検討する。単純な 1 対 1 の対応には過剰 |

共通の決まりは 3 つ。無名関数をその場で表に詰めない。関数名だけで何の処理か分かる名前を付ける。1 行に複数ケースを書かない。

もう 1 つ、差し替える関数の中に「100 円引き」のような業務上の数値を直書きしない。数値は定数ファイルか設定ファイルに名前を付けて置き、関数は計算の形だけを持つ。DB の設定テーブルにするのは指示されたときだけ。判断表は `references/business-values-placement.md`。

## 複数候補が当たったときの選び分け

### Adapter と Facade と Proxy と Decorator
4 つとも、間に 1 枚挟む形になる。挟む理由が違う。
- Adapter は、呼び出し方が合わないものを合わせるために挟む。外部の形をこちらの形に変換する。
- Facade は、複雑な手順を単純な窓口にまとめるために挟む。上の判断基準を満たすときだけ。
- Proxy は、本人の代わりに代理人が要求を受けるために挟む。遅らせる、止める、代わりに答える。
- Decorator は、中身を変えずに機能を重ねがけするために挟む。同じ形のまま処理を足す。
各ページに相互の比較の記述は無いので、この使い分けは各ページの目的の記述から読み取ったもの。

### State と「アルゴリズムの差し替え」
状態の遷移があるなら State。切り替えたいのがアルゴリズムだけなら、Strategy という名前を付けずに「関数を渡す」と書く。
基本ページには、Strategy は「戦略」を、State は「状態」をクラスとして抽出すると書かれている。

### Observer と Mediator
Observer のページに、Mediator の一部でも同様の通知の仕組みが使われていると書かれている。
まず Observer で組む。部品どうしのやりとりが双方向・多方向になって、互いに条件を見合うようになったら Mediator に進む。

### Command と「取り消し」
あとで実行したい、キューに積みたい、取り消したい、なら Command。
状態を丸ごと戻したいだけなら Memento という名前を付けず「過去の状態を配列で持つ」と書く。

### Composite と Interpreter
Interpreter のページに、Composite と同じ構造を使うと明記されている。
木構造を扱いたいなら Composite。書式を解析して実行したいなら、Interpreter を自作せず既存のパーサライブラリに任せる。
