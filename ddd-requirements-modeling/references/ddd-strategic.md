# 業務の分け方と言葉のそろえ方

業務ごとに何を扱うかを決め、必要な情報を受け渡せる全体像を作る。
用語の表記は `../SKILL.md` の「用語の統一」に従う。

## 業務領域を見つける

業務領域は、事業の中で関連する仕事をまとめた範囲を指す。まず、誰が何のために使うシステムかを要件から読み取る。

1. 要件に登場する仕事、担当者、外部システム、扱う情報を拾う。
2. 同じ担当者が同じ情報を使って進める仕事をまとめる。
3. まとまりごとに、業務で使っている名前を付ける。
4. 作り方や担当範囲の判断が変わる場合に、さらに細かく分ける。

部門名や画面名は手がかりとして使う。部門や画面ごとに必ず業務を分けるわけではない。
分けても作る範囲や実装方式が変わらなければ、それ以上細分化しない。依頼の対象外の業務は設計に足さない。

## 中核・一般・補完の判断

| 種類 | 判断すること | 設計の方針 |
|---|---|---|
| 中核 | 独自の方法や業務ルールが、競合との差や顧客に選ばれる理由になるか | 自前で作り込む候補。価値を生むルールを詳しく確認する |
| 一般 | 多くの会社で共通する仕事で、必要な条件を満たす既製品があるか | 既製品や外部サービスを第一候補にする |
| 補完 | 事業には必要だが差別化にはつながらず、個別の仕組みが必要か | 素直に作る。複雑な仕組みを先に入れない |

判断の根拠は要件にある言葉や確認できた事実を書く。競合や差別化の記述がない場合は「（仮）」を付ける。
認証や決済などの機能名だけでは確定しない。独自の業務条件があるか、既製品で満たせるかを確認する。
売上に関係することや、実装が複雑なことだけを中核の理由にしない。価値を生むのが人の判断で、システムは記録を扱うだけの場合もある。
分類は実装方式と突き合わせる。食い違いがあれば、分類に合わせて実装を複雑にせず、未確認の要件を質問する。

## 同じ言葉を決める

同じ言葉は、業務担当者と開発者が同じ意味で使う言葉を指す。
要件、図、操作名、データ名で表記をそろえる。業務の説明には、担当者が使っている言葉を優先する。

| 見つかった状態 | 確認すること | 整理すること |
|---|---|---|
| 同じ言葉に複数の意味がある | 誰がどの場面で使い、何を指すか | 意味ごとに分け、適用する範囲を決める |
| 違う言葉が同じ意味に見える | 区別する業務上の理由があるか | 同じなら表記をそろえ、違うなら違いを残す |
| システム都合の名前しかない | 業務ではその対象を何と呼ぶか | 業務で通じる名前に対応付ける |
| 名前は分かるが動作が不明 | 誰が何をすると、何が変わるか | 必要な動作の表で操作と結果を補う |

意味が複数ある言葉を先に整理し、主な用語は10個以内にする。要件の名詞をすべて用語集に並べない。
構造体に持たせる情報も、その業務の目的に必要な範囲に絞る。現実の対象について分かることを全部持たせる必要はない。

## 区切られた文脈を決める

区切られた文脈は、言葉の意味と業務ルールを一貫して扱う範囲を指す。
まず広い範囲から考える。次の根拠がある箇所で分割を検討する。

| 分ける根拠 | 確認すること |
|---|---|
| 同じ言葉の意味が違う | 必要な情報やできる操作も異なるか |
| 別チームが独立して担当する | 変更の責任者と受け渡す情報を決められるか |
| 別システムが情報を管理している | どちらが情報の正しさを管理し、相手から何を受け取るか |

画面数、テーブル数、コード量だけを理由に分けない。分ける根拠が不明ならまとめたまま仮置きする。
同じ情報を使う一連の仕事を分割した結果、毎回双方の修正が必要になるなら境界を見直す。
業務領域は仕事の分類であり、文脈は情報の扱い方を分ける設計上の境界である。必ず一対一にそろえる必要はない。
複数の業務を1つのアプリの中にモジュールとして置いてもよい。文脈を分けたことだけを理由に、別サービスや別DBを必須にしない。

## 文脈どうしのつながり方

情報や機能を提供する側を供給者、使う側を利用者とする。
何を渡すか、どちらの言葉やデータ形式を使うか、変更を誰と調整するかを決める。

| 連係方法 | 選ぶ条件 | 決めておくこと |
|---|---|---|
| 良きパートナー（Partnership） | 双方が協力して受け渡し方を変更できる | 変更の連絡と双方への反映方法 |
| モデルの共有（Shared Kernel） | 双方で同じ意味の情報やルールを共有する必要があり、変更を調整できる | 共有範囲を必要な部分に絞り、変更時に双方への影響を確認する |
| 利用者と供給者（Customer-Supplier） | 提供側と利用側に役割が分かれる | 利用側の要望を、供給側がどこまで反映するか |
| 従属（Conformist） | 供給側の形式がこちらの用途に合い、そのまま受け入れられる | 相手の変更に追随する範囲 |
| モデル変換装置（Anticorruption Layer） | 相手の形式や意味をそのまま使うと、こちらの業務を表現しにくい | 利用側で変換する項目と対応関係 |
| 共用サービス（Open Host Service） | 提供側が複数の利用者に安定した受け渡し方を提供する | 内部の都合から分けた公開形式と変更時の扱い |
| 互いに独立（Separate Ways） | 連係の必要がなく、共有や調整の負担が便益を上回る | 共有しない範囲。必要な情報の受け渡しまで省かない |

公開された言葉（Published Language）は、文脈間で合意したデータ形式や用語を指す。共用サービスなどの受け渡しに使う。
中核の情報でも共有を自動的に選ばない。意味が異なる情報を無理に共通化せず、必要なら受け取る側で変換する。
モデルを共有する場合は、共有部分の変更でどの利用者に影響するかを確認できるようにする。

## 全体図に反映する

- 文脈を外枠にし、集約のルートを中の箱に置く。
- 矢印は材料を渡す向きに引く。出来事を知らせる場合は点線を使う。
- 文脈をまたぐ矢印には連係方法を付ける。
- 下流から上流へのID参照は、集約の表で示す。

図と表の列は `../assets/output-template.md` に従う。全体図を作る段階で、各クラスや関数の呼び出し手順まで決めない。

## 未確認のときに聞くこと

必要な質問を選び、スキル全体で最大8個に絞る。

| 不明なこと | 質問で確認する内容 | 決まること |
|---|---|---|
| 中核かどうか | 顧客に選ばれる理由や独自の業務ルールは何か | 業務の分類と作り込む範囲 |
| 言葉の意味 | 誰がどの場面で使い、何を指しているか | 用語と文脈の境界 |
| 情報の管理者 | どのチームやシステムが正しい情報を管理するか | 更新の責任と連係の方向 |
| 相手との関係 | 相手のデータ形式を変更できるか、そのまま利用できるか | 連係方法 |
| 既製品の利用 | 必要な条件を既存の製品やサービスで満たせるか | 自前で作る範囲 |
