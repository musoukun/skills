# 集約と保存の決め方

業務で中心となる情報と、その情報が守る決まりをひとまとまりとして整理する。
ここでは必要なデータと保存の境界を決める。細かいクラス分けは、要件が固まり必要性が分かってから考える。

## 集約を見つける手順

集約は、同時に守らなければならない決まりを扱う最小のまとまりを指す。
不変条件は、操作後も必ず成り立っていなければならない業務の決まりを指す。

1. 要件から中心となる対象と、その対象を区別するIDを拾う。
2. 対象が持つ情報、取り得る状態、できる操作を整理する。
3. 操作の前後で守る必要がある決まりを書き出す。
4. 決まりの判定に必要な情報と、一緒に更新しなければならない情報を集める。
5. 各情報について、古い値のまま判定したら何が起きるかを確認する。
6. 常に最新でなければ決まりを破る情報を、保存や同時更新の設計に含める。後から反映しても問題ない情報は集約の外に出す。
7. まとまりを代表する対象を集約のルートにし、他の集約はIDで参照する。
8. 外に知らせる必要がある出来事を、過去形の業務イベントとして整理する。

中心となる情報は、普通の構造体として表現してもよい。構造体を作っただけでは、同時更新や保存時の決まりは保証されない。どの処理が決まりを確認するかも決める。

## 集約の境界ルール

| 確認すること | 判断すること |
|---|---|
| その情報を含める理由 | 決まりの判定や同時更新に必要なものを含める。一緒に表示することは、含める理由にならない |
| 状態を変更する方法 | 決まりを検証する操作を通す。直接の書き換えによって検証を飛ばせる設計にしない |
| 変更を受け付ける対象 | 集約のルートを通して内部の情報を扱う。外部が内部の部品を別々に更新しない |
| 保存する範囲 | 集約内の一連の変更は、全部成功するか全部取り消すかのどちらかにする |
| 複数人が同時に変更する場合 | 古い状態に基づく更新で、先に保存された変更を上書きしない。DB側の同時更新対策を決める |
| 他の集約の情報が必要な場合 | IDで参照する。古い情報での判定が許されないなら、境界と保存方法を見直す |
| 複数の集約を一緒に確定したい場合 | 本当に同時に守る決まりがあるかを確認し、集約の境界を再検討する |
| 後から反映してよい場合 | 別の集約として扱い、業務イベントなどで伝える。反映の遅れが許される条件を確認する |
| 集約が大きい場合 | 決まりを守るために必要な範囲まで小さくする。関係があるだけの情報を取り込まない |
| 履歴や予約が増え続ける場合 | 期間などで区切る案を検討する。区切りをまたぐ決まりも確認する |
| 外部に知らせる場合 | 確定した出来事と、受け手に必要な情報を示す。保存前の状態を確定した出来事として知らせない |
| 名前を付ける場合 | 対象、項目、操作、出来事に、該当する文脈の同じ言葉を使う |

DB側の対策には、更新前の版番号を確かめる方法や重複を禁止する制約などがある。どれが必要かは、守る決まりと実際のDBの機能に合わせて決める。
例えば予約の重複禁止は、予約1件の項目を確認するだけでは守れない。複数の予約が同時に登録される場合にも、重複を防げる保存方法が必要になる。これは説明用の例であり、予約機能を要件に追加する指示ではない。

## 細かい部品を検討するとき

採用する時期と値オブジェクトの必要性は、`../SKILL.md` の「構成要素の粒度」と「値オブジェクトの採用」に従う。

| 部品 | 何を表すか | 検討する理由 |
|---|---|---|
| 値オブジェクト（Value Object） | IDではなく値の組み合わせで同じものと判断する情報。変更時は新しい値として扱う | 検証・計算・比較の決まりをひとまとまりにする利点がある |
| エンティティ（Entity） | 内容が変わっても、IDで同じ対象として追い続ける情報 | 集約の内部にも、個別に区別する対象がある |
| 業務サービス（Domain Service） | 特定の集約や値に置きにくい業務の計算や判断 | 複数の集約を参照する計算などを、名前付きの処理としてまとめる必要がある |
| リポジトリ（Repository） | 集約の取得と保存を扱う窓口 | 保存の都合を業務の判断から切り離す具体的な必要がある |

部品名が当てはまることと、専用クラスが必要なことは別に判断する。普通の型・構造体と関数で足りるなら、その形にする。
業務サービスを作っても保存の境界は変わらない。複数の更新を途中まで確定してよい理由にはならない。

## 操作と保存の役割

業務の処理を実行する側は、必要な情報を読み、決まりを守る操作を実行し、その結果を保存して呼び出し元へ返す。
業務上の判断を扱う処理と、DBや外部サービスの呼び出しを扱う処理は、役割が読み取れる形にする。
業務ルールが複雑なら、判断する処理をDBや画面の都合から切り離す。層の数や専用インタフェースの数を先に決めない。

## テーブルの当たりを付ける

| 項目 | 仮の設計で書くこと |
|---|---|
| 集約との対応 | どのまとまりを保存するテーブルか |
| 主キー | 対象を区別するID |
| 最低限の列 | 状態、金額、日時など、決まりを守るために必要な情報 |
| 一意制約 | 重複させてはいけない組み合わせ |
| 履歴 | 何を残す必要があるか。現在の状態で足りるか |
| 削除 | 消してよいか、削除した記録を残すか |
| 外部のID | 別システムの対象とどう対応付けるか |
| 時刻 | 日付で扱うか時刻まで必要か。どの地域の時刻で判断するか |

列の型や桁、細かな索引はこの段階で確定しない。受付番号や伝票番号は、アプリで最大値に1を足さず、DBかORMの採番に任せる。
業務上の数値の置き方は `business-values-placement.md` に従う。

## 履歴から状態を再現する場合

イベント履歴式ドメインモデルは、確定した出来事を順に保存し、その履歴から状態を再現する方式である。
現在の状態と通常の履歴保存で足りるかを先に確認する。金額の項目があることだけで採用しない。
実装方式の選び方は `ddd-heuristics.md` の「実装方式の判断」に従う。

採用する場合は、次の流れを設計する。

1. 対象の出来事の履歴を読み込む。
2. 履歴を順に反映して、判断に使う現在の状態を作る。
3. 操作を検証し、新たに確定する出来事を決める。
4. 同時更新の衝突を確認し、出来事を保存する。

| 確認する条件 | 設計に反映すること |
|---|---|
| 過去の状態を再現する | 保存する出来事に、再現に必要な情報を含める |
| 判断の理由を追いたい | 何が変わったかに加え、業務上必要な理由を残す |
| 履歴の形式を変える | 古い形式の履歴を読み続ける方法を考える |
| 履歴が大きくなる | 集約の範囲を確認する。再現に時間がかかる事実があれば途中の状態を保存する方法を検討する |
| データの削除が必要 | 履歴の保持と削除の要件が両立するか確認する |

## 外部への通知と複数の業務の連係

追加する仕組みは、要件上の必要があるときに選ぶ。設計書では実装方式の補足に書き、11パターンの提案表には混ぜない。

| 必要なこと | 候補と役割 |
|---|---|
| 相手の情報をその場で変換する | 状態を持たない変換処理 |
| 複数の情報がそろってから渡す | 途中の情報を保持してまとめる変換処理 |
| DB保存後の通知漏れを防ぐ | 送信箱（Outbox）。更新と送信予定を一緒に保存し、後から送る |
| 別々に確定する業務を連係し、失敗に対応する | サーガ（Saga）。必要な取り消しや代替処理を決める |
| 待ち合わせや分岐を含む進行を管理する | プロセスマネージャー（Process Manager）。進行状況を保持して次の処理を決める |
| 更新に使う情報と一覧・集計の形が大きく違う | コマンド・クエリ責任分離（CQRS）。更新用と参照用の扱いを分ける |

送信箱を使う場合は、更新内容と送信予定を同じトランザクションで保存する。送信担当の処理が予定を読み、送信後に完了を記録する。再送で同じ通知が届いても二重処理にならないよう、受信側の扱いも決める。
サーガで連係する業務は、別々に結果が確定する。一瞬の不一致も許されない決まりを、後から取り消す処理で代用しない。
参照用の情報を後から更新する場合は、表示が遅れることを業務が許容できるか確認する。保存直後の結果を返すときは、確定した更新内容を使う。

## 境界が決まらないときの質問

| 不明なこと | 確認する内容 |
|---|---|
| 守る決まり | 何が起きると業務として困るか。どの状態は保存してはいけないか |
| 同時更新 | 同じ対象を複数人が操作したら、両方成功してよいか |
| まとまり | 一緒に確定しなければならない情報はどれか |
| 古い情報 | 判定に使う情報が古いと、誰に何が起きるか |
| 部分的な失敗 | 途中まで成功してよいか。失敗したら何を取り消すか |
| 通知 | 誰に何を、いつまでに知らせる必要があるか |
| 履歴 | 過去の状態や判断の理由を、どこまで再現する必要があるか |

質問は全部を並べず、答えによって図や表が変わるものを選ぶ。
